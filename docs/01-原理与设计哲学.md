# 01 · 原理与设计哲学

> 这份文档回答：**为什么这个 skill 要这么设计，而不是让 AI 直接改。**

---

## 一个所有用过 AI 改作文的老师都遇到过的问题

直接把一篇作文扔给 AI，说「帮我改改」，你会得到什么？

一段看起来很像样的批改——但仔细一核对，问题就出来了：

1. **评分没有依据**。「这篇写得不错，大概 B1 水平」——B1 的哪一档？四个维度分别多少分？AI 说不出来，因为它没在用量表，它在凭感觉。
2. **手写认错字不改**。手写的 `happly` 被 AI 读成 `happy`，然后 AI 告诉你「这篇作文拼写全对」。你以为是学生写对了，其实是 AI 认错了。
3. **反馈是 AI 腔**。「这不仅体现了你的词汇量，而且彰显了你对语法的掌握」——这种话发给家长，家长一眼看出是机器写的，老师没有面子。
4. **每次结果不一样**。同一篇作文，上午问和下午问，分数可能差两分——因为没有任何机制保证一致性。

这个 skill 的设计，就是为了解决这四个问题。

## 设计哲学：流程约束 > 模型能力

我们不相信「更聪明的模型就能改对」。我们相信的是：

**一个够笨、够死板的流程，比一个够聪明的模型更可靠。**

所以整个 skill 的思路不是「让 AI 更聪明」，而是「给 AI 立规矩」——每一步能做什么、不能做什么、做到什么程度算合格，全部写死。AI 在这个框架里执行，出错的空间被压缩到最小。

这带来一个直接的好处：**换模型也能用**。这个 skill 不依赖任何一个特定模型的能力，只依赖流程本身。你在 Kimi、Claude、Codex 上跑，出来的结果应该是一样的——因为流程是同一个。

## 六个核心原则

### 原则 1：先确认，再评分

手写作文识别永远不可能 100% 准确。这个 skill 不追求「识别得更准」，而是追求「认错之前先让你看一眼」。

流程里有一个强制停点：AI 转写完作文、报完字数之后，**必须停下来等你确认**。你扫一眼，有认错的字就纠正，没错就放行。评分只在确认之后进行。

代价：多一步操作，多 10 秒。收益：杜绝「AI 认错字导致误判」这类最冤枉的错误。

### 原则 2：评分必须挂在官方量表上

每一项分数都必须能说出「为什么是这个分，依据剑桥官方教师指南的哪一条 band descriptor」。说不出依据的分，不许给。

rubric 文件里存着三套官方量表（KET / PET / FCE）的 band descriptor、官方样文锚点（真实评过分的样文+评语）、以及教研共识和自定规则。给分时先对照锚点，再写依据。

### 原则 3：字数是硬线

写不满词数线，直接判不过。没有「酌情通过」。

PET 不足 90 词、KET 邮件不足 25 词 / 故事不足 35 词、FCE 不足 140 词——这是**自定规则**（剑桥官方没有这个硬线），但它解决一个真问题：学生不知道「写满字数」是底线，你不立这条线，他永远写不够。

判不过不等于结束：批改、范文、反馈照常产出，孩子知道怎么改，只是把「没到字数线」这个结论明确告诉他。

### 原则 4：学生版输出是纯文本，没有 AI 腔

给家长的反馈不是「显得专业」，是「能直接用」。所以这个 skill 对学生版反馈有三条红线：

- **纯文本**，不用 Markdown 表格和标题（微信里会变乱码）
- **禁破折号**（—— 和 —）
- **禁「不是…而是…」「不仅仅…更…」**这类 AI 对比句式

评语要像老师平时说话，具体到语言点，亮点必须真实（从原文找），不写「书写工整」凑数。

### 原则 5：两个交付物，内容不重复

这个 skill 交付两个独立的东西：

| 交付物 | 给谁 | 内容 | 形式 |
|---|---|---|---|
| 学生版纯文本反馈 | 学生/家长（微信） | 定稿格式五分区，简洁 | 对话里直接输出 |
| HTML 批改报告 | 家长/存档 | 完整批改档案：原题、原文、逐句批改、范文、详细评价 | 独立 HTML 文件 |

两者的关系：**互补，不重复**。学生版反馈不进 HTML 报告；HTML 报告里放的是微信里塞不下的细节（比如「Content 为什么给 2 不给 3」的完整论证）。

### 原则 6：机器卡口兜底

人（和 AI）都会犯错，所以每次交付前有一道机械检查：

- 学生版反馈：五分区齐全、顺序对、无破折号、无 AI 句式、星级递减、分数算数对（小分和=总分、档位与分数匹配）
- HTML 报告：六区块齐全、分数区和文本反馈一致、没有学生版反馈段回流、没有占位符
- 跨文件一致性：两个交付物的总分、小分、结论必须对得上

校验器不过，不许交付。这条不是建议，是写死在流程里的。

## 为什么是「工作流」而不是「工具」

这个 skill 不是一个软件、一个 API、一个 App。它是一套**提示词工作流 + 规则文件 + 校验脚本**，跑在你已有的 AI 助手（Kimi Code / Claude Code / Codex）里。

选择这个形态的原因：

1. **零安装成本**——复制一个文件夹就能用，不依赖服务器、账号、API key
2. **完全可审计**——所有规则都是 Markdown 文本，你可以逐条读、逐条改
3. **可定制**——字数硬线、档位划分、反馈格式，都是明文，想改就改
4. **跨模型**——流程不依赖特定模型，换 AI 助手也能用

代价是你需要有一个 AI 助手环境（上面三个之一）。如果你只用网页版 ChatGPT / Kimi，这个 skill 暂时用不了——这是当前的真实边界。

## 和「直接让 AI 改」的本质区别

| | 直接让 AI 改 | 用这个 skill |
|---|---|---|
| 转写 | 可能认错字，不告诉你 | 转写后停住等你确认 |
| 评分 | 凭感觉，给不出依据 | 挂官方量表+锚点，逐项给依据 |
| 字数 | 不查 | 硬线，写不满判不过 |
| 反馈 | 可能有 AI 腔 | 禁破折号、禁 AI 句式、纯文本 |
| 一致性 | 每次可能不同 | 机器校验器兜底，格式分数强制一致 |
| 报告 | 没有 | 可生成 HTML 报告发家长 |

这个 skill 不承诺「改得比你准」。它承诺的是：**把批改中最机械、最容易错、最耗时的部分标准化，让你把精力留给只有老师能做的事**——判断这个学生的问题是个案还是共性、设计下一节课怎么补、跟家长解释这个分数意味着什么。
